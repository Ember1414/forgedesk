# ADR-002: 私有仓库起步 + 两阶段 CI 配额策略

- 状态：已接受
- 日期：2026-09-23
- 里程碑：M0 / T0.10
- 关联：`docs/PLAN.md` §11.1、§11.2；`docs/OPEN-SOURCE-READINESS.md`；`.github/workflows/ci.yml`

## 上下文

项目决定**先以私有仓库开发，待落地后再转为公开**（人类决策，2026-09-23）。

这带来两个必须处理的约束——它们不是"服务器设置问题"，而是会直接改变工程决策的硬约束：

### 约束一：GitHub Actions 配额与 Runner 计费倍率

公共仓库的 standard runner 用量不计费；私有仓库在 GitHub Free 计划下为 **2000 分钟/月**，
且不同平台的 runner 按**倍率**消耗配额（数值需以 GitHub 官方最新定价为准）：

| Runner | 计费倍率 | 一次三平台 Tauri 构建的近似消耗 |
| --- | --- | --- |
| `ubuntu-*` | 1x | ≈ 8 配额分钟 |
| `windows-*` | 2x | ≈ 24 配额分钟 |
| `macos-*` | 10x | ≈ 100 配额分钟 |
| **合计** | — | **≈ 132 配额分钟 / 次** |

若每个 PR 都跑三平台矩阵，2000 分钟配额只够约 15 次运行；叠加 E2E 与夜间任务会迅速耗尽。
更糟的是：配额耗尽后 CI 直接不可用，而"CI 不可用"会破坏 M0 出口标准。

### 约束二：GitHub Pages 在私有仓库下不可用

GitHub Pages 在 Free 计划的**私有**仓库中不提供（需要 Pro/Team/Enterprise）。
本项目的 M7（官网、更新清单托管）与 M8（下载页、校验和）都依赖 Pages。

> **后续更新（2026-09-23）**：本约束已被 `docs/adr/ADR-003-cloudflare-instead-of-github-pages.md`
> **部分解除**——官网与更新清单改用 Cloudflare Pages（免费且支持私有仓库场景），
> 因此这两项任务不必后移到转公开之后。本条保留以记录当时的判断过程。

## 决策

**采用两阶段 CI 策略，并把 Pages 相关任务整体置于"转公开之后"。**

### 私有阶段（当前）

| 触发 | 运行内容 | 理由 |
| --- | --- | --- |
| `pull_request` | 仅 Linux 质量门禁（1x） | 门禁的核心价值是"拦住坏代码"，Linux 上的 lint/typecheck/test/clippy/cargo test 已能覆盖 |
| `push to main` | 质量门禁 + 三平台构建 | 保证主干始终可构建；频率低（每次合并一次） |
| `workflow_dispatch` | 手动按需 | 排查平台问题时用 |
| ~~夜间任务~~ | **不启用** | 私有阶段属于纯消耗，收益不足以抵扣配额 |
| 三平台**打包**（安装包） | **不在此阶段做** | 打包还需下载 WiX/NSIS；由打 tag 时的 release 工作流负责（T0.11 / T7.3） |

### 公开阶段（转公开后）

1. 删除 `build` job 上的 `if: github.event_name != 'pull_request'`，恢复"每个 PR 都跑三平台矩阵"。
2. 启用 `e2e.yml`（Linux 必需）与 `nightly.yml`（全量 + 性能基准）。
3. 启用 GitHub Pages（M7/T7.9）与更新清单托管（T7.1/T7.3）。
4. 执行 `docs/OPEN-SOURCE-READINESS.md` 中的全部审计项。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 直接在公共仓库开发 | CI 免费无限、Pages 可用、天然接受外部审视 | 与人类"先私有"的意图冲突；早期代码与内部讨论过早曝光 | 否（人类已决定） |
| B. **私有起步 + 两阶段 CI** | 符合意图；配额可控；CI 配置一次写好，转公开只需删一行 `if` | 私有期拿不到 macOS/Windows 的持续验证；Pages 相关任务后移 | **采用** |
| C. 私有起步 + 自建 runner | 配额不受限 | 需要一台常驻机器与运维，违反"零成本/零运维" | 否 |
| D. 私有起步但完全不做 CI | 省配额 | 破坏 M0 出口标准；主干可构建性失去保障 | 否 |

## 后果

**正面**

- 免费配额被用在最高价值处（PR 门禁 + 主干三平台构建）。
- `.github/workflows/ci.yml` 与 `scripts/ci/validate-workflows.mjs` 一次写好，转公开只需删一行。
- 新增的工作流校验器会强制每个 job 声明 `timeout-minutes`，从机制上防止"挂死任务烧配额"。

**负面 / 需要接受的代价**

- 私有阶段 macOS 与 Windows 的构建只在合并到 main 时验证，PR 阶段发现不了平台特定问题。
  缓解：本地（Windows）已有完整工具链；macOS/Linux 问题在合并时暴露。
- Pages 相关任务（官网、更新清单、下载页）在转公开前无法完成，M7/M8 的部分交付物被推迟。
  这不影响 v1.0 的**功能**完成度，只影响**分发基础设施**。
- 转公开前必须做一次内容审计，因为 **git 历史会随仓库一起公开**（见 `docs/OPEN-SOURCE-READINESS.md`）。

**需要后续跟进**

- 转公开时按清单逐项执行，并把本 ADR 状态改为"已被 ADR-00X 替代"或补充"公开阶段已生效"。
- 若未来引入付费计划（Pro），需重新评估 Pages 与配额约束是否仍然成立。
