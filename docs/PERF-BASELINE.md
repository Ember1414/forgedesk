# M1 性能基线（T1.12 第 4 条）

本文件记录 M1 收官时的一组**可复现**测量：怎么量的、量到了什么、哪些结论不能从中得出。

- 测量日期：2026-09-27
- 机器：Windows（x86_64-pc-windows-msvc），release 构建（`cargo build --release`）
- git：系统 CLI（与用户终端同一个）
- 被测代码：`forgedesk-services` 的真实服务栈（`RepositoryService` / `WorkspaceService` /
  `StagingService` + 真实 `GitEngines`），通过 `crates/services/examples/perf_probe.rs` 调用

> T2.9 的补测见 §5：历史侧指标、日志分页缓存的前后对照、性能模式与 nightly 门禁。

## 1. 怎么量

```powershell
# 1) 生成夹具（可复现：同一 N 每次生成同样的提交 oid）
node scripts/perf/gen-repo.mjs target/perf/commits-100000 --commits 100000
node scripts/perf/gen-repo.mjs target/perf/modified-10000 --modified 10000
node scripts/perf/gen-repo.mjs target/perf/untracked-10000 --untracked 10000

# 2) 构建探针并跑基线（内存与 CPU 由脚本从进程外部采样）
cargo build --release -p forgedesk-services --example perf_probe
powershell -NoProfile -File scripts/perf/run-baseline.ps1 -WatchSeconds 5
```

探针量四个动作，全部在**同一个进程**内完成（因此 `openMs` 包含了引擎初始化后的
首次仓库读取）：

| 指标 | 含义 |
| --- | --- |
| `openMs` | `RepositoryService::open`：发现仓库 + 配置审计 + git 版本检查 + 登记 |
| `statusMs` | `WorkspaceService::status`：状态面板一屏所需的数据 |
| `diffMs` | 单文件完整 diff（打开查看器那一次请求） |
| `stagingMs` | 整文件暂存 + 取消暂存各一次（写路径 + 补丁通道） |
| `watchCpuMs` | 启动文件监听后**空闲** 5 秒所消耗的 CPU（外部采样 `TotalProcessorTime`） |
| 峰值内存 | 外部采样 `WorkingSet64` 的最大值（含 git 子进程之外的一切） |

## 2. 结果（`target/perf/baseline.json` 的汇总）

| 仓库 | 形状 | openMs | statusMs | diffMs | stagingMs | 峰值内存 | 监听空闲 CPU / 5s |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| commits-100 | 100 提交 | 313 | 12.8 | – | – | 8.2 MB | 62 ms |
| commits-1000 | 1k 提交 | 299 | 11.0 | – | – | 8.1 MB | 0 ms |
| commits-10000 | 10k 提交 | 300 | 11.5 | – | – | 8.0 MB | 62 ms |
| commits-50000 | 50k 提交 | 312 | 9.6 | – | – | 8.1 MB | 78 ms |
| commits-100000 | 100k 提交 | 301 | 11.6 | – | – | 8.1 MB | 31 ms |
| modified-10000 | 10k 已跟踪修改 | 299 | **6168** | 112 | 510 | 17.0 MB | 47 ms（见下） |
| untracked-10000 | 10k 未跟踪 | 302 | 376 | – | – | 14.8 MB | 78 ms |
| forgedesk | 本仓库（真实，16 条变更） | 286 | 72 | 101 | 74 | 8.4 MB | 109 ms |

读法（这几条是结论，不是数字游戏）：

1. **`openMs` 与仓库规模无关**（286–317 ms，抖动在测量噪声内）：它是固定成本
   （git 版本探测 + 配置审计各起一次 git 子进程），不是"读了多少历史"。
   M1 验收的"打开仓库 ≤ 2s 显示状态"因此有大量余量。
2. **状态刷新的成本由"变更文件数"决定，而不是"提交数"**：10 万提交的仓库
   状态刷新 11.6 ms，与 100 提交的仓库没有区别——状态只读索引与工作区。
3. **监听空闲时 CPU ≈ 0**：5 秒窗口内 0–109 ms（约 0–2% 单核），
   与仓库规模无关（10k 文件与 100k 提交都一样）。这是 T1.10 的"大仓库空闲占用接近 0"
   验收项，此前只能靠推理，现在有实测。
4. **内存峰值 8–17 MB**：10k 变更条目时约 17 MB（每个条目一条 DTO + 路径），
   仍然远低于任何值得担心的量级。
5. **`statusMs = 6168 ms` 是本基线的唯一红灯**：见下一节。

## 3. 已知问题与结论边界

### 3.1 10k 已跟踪修改时，状态刷新 6.2 秒（P1，待决策）

同一仓库 `git status --porcelain` 只用 **0.61 秒**。差异来自**读路径走 libgit2**
（T1.2 的设计：读用 libgit2、写用 CLI）：libgit2 在"索引 1 万条、工作区全改"
这一形状上比 git CLI 慢约 10 倍。

排查过程中的两次对照（同一台机器、release 构建、热身后）：

| 配置 | statusMs | 说明 |
| --- | ---: | --- |
| 当前实现 | 6168 ms | 富化 + libgit2 状态 |
| 临时禁用富化 | 5813 ms | 说明瓶颈在 libgit2，不在我们的富化 |
| 富化中**去掉二进制嗅探**（已修） | – | 修复前该动作每次状态刷新要**打开并读取每个文件**，在 1 万文件上量到 39–47 秒 |

**已修的部分**（本任务内）：`crates/git-engine/src/engine/enrich.rs` 不再对每个条目做
二进制嗅探（`File::open` + 读 8KB）。git 自己也不在 `status` 里判二进制；
真正需要它的地方（diff、`git apply`）本来就有 git 的判定。

**未修的部分**（需要产品/架构决策，不在 T1.12 单方面改动）：

- 方案 A：把 `status` 也切到 CLI 引擎（0.61 s）。代价：改变 T1.2 "读用 libgit2"
  的划分，且 CLI 引擎的状态路径没有富化（文件大小、操作状态），界面会少两个字段；
- 方案 B：按规模分流（索引条目超过阈值时用 CLI，小仓库继续 libgit2）。
  代价：引入了运行时两条路径，差分测试之外的组合变多；
- 方案 C：接受 6.2 s，界面用骨架屏 + 明确进度提示覆盖这段时间。

在决策之前，界面侧的验收（10k 行渲染不卡顿）**是过的**：
`e2e/workspace.spec.ts` 的 "10000 个变更文件的首屏渲染（性能基准）" 用例通过。

### 3.2 未跟踪目录的表示与 git 不同（P1，待决策）

libgit2 的 `recurse_untracked_dirs(true)` 会**逐个列出**未跟踪目录里的文件
（1 万个文件 = 1 万条），而 `git status` 默认把它们折叠成一条 `scratch/`。
因此同一仓库、同一时刻，"未跟踪"分组的条目数可能比用户在终端里看到的多。
数字上我们的路径更快（376 ms），但**语义与 git 不一致**。
修复选项：`recurse_untracked_dirs(false)`（与 git 对齐，但会改变 T1.4 的未跟踪列表形状）。

### 3.3 这组数字不能证明什么

- 它是**单机、单次**测量（每个仓库一次，冷启动一次已被 3.1 表剔除）。
  可信的是量级与相对关系，不是小数点后一位；
- 磁盘是本地 SSD。网络盘、加密盘上的 `status`/`diff` 会明显更差；
- `openMs` 里的 git 子进程启动成本在 Windows 上偏高（约 150–250 ms）。
  Linux/macOS 上会低得多，因此**不要**把这里的绝对值当作跨平台指标；
- 没有量：终端（M5）、大文件 diff 的渲染（M5）。历史图（M2）原本也在这个
  清单里，T2.1/T2.2 收官时已补测，见 §4。

## 4. M2 补测：历史布局与提交图渲染（T2.1 / T2.2）

测量日期：2026-09-28，机器同上（Windows 开发机）。§3.3 "没有量"清单里的
"历史图"一项由本节补上。

### 4.1 泳道布局（Rust，纯逻辑，`forgedesk-domain`）

```powershell
cargo test --release -p forgedesk-domain --all-features -- --ignored --nocapture
```

输入形状：固定种子 xorshift 随机 DAG（max_parents = 3）——**刻意的最坏情况**：
它会产生约 1.9 万条并发泳道（真实仓库典型 < 50 条），布局复杂度 O(V·lanes)，
在随机 DAG 下近似 O(V^1.8)。门槛写在测试断言里（5000 < 200ms、50000 < 15s、
100000 < 60s），本次实测：

| 规模 | 实测 | 边数 | 并发泳道 |
| --- | ---: | ---: | ---: |
| 5,000 | 52.3 ms | 10,036 | 1,943 |
| 50,000 | 7.2 s | 100,270 | 19,170 |
| 100,000 | 26.4 s | 199,636 | 38,537 |

读法：随机 DAG 是压力上限而非产品路径。真实仓库分支浅、单父提交占绝大多数，
远快于上表；且服务层每页 ≤ 500 行（`MAX_PAGE_SIZE`），单页布局在毫秒级以下。
"全量布局 26 秒"只存在于 10 万提交全开 `--all` 的极端合成场景，界面正常使用
永远不会一次性触发它（折叠模式的祖先集判定也只在末页做一次）。

### 4.2 提交图渲染（前端，dev 构建 + mock IPC）

```bash
PERF_BENCH=1 npx playwright test e2e/graph-bench.spec.ts
```

方法：mock `git_log_page` 一次性返回整段历史（8 条泳道），让前端模型直接承载
目标规模。口径：**热首屏** = reload 后从导航到"图可见 + 行数就位"——它包含
**页内重新生成 5 万 / 10 万行夹具**与整个 app 启动，因此偏保守（真实场景的
提交数据来自 IPC，没有夹具生成这一步）；冷首屏含 dev server 模块转换与浏览器
脚本编译（一次性成本，不代表稳态）。数字看 stdout 的 `[BENCH]` 行，
下表为 2026-09-28 三次运行的区间：

| 规模 | 热首屏（3 次） | rAF fps（静止 / 滚动） | 面板 fps | 静态层/帧 | 动态层/帧 | 堆内存 |
| --- | --- | --- | ---: | ---: | ---: | --- |
| 50,000 | 1013–1177 ms（门槛 <1.5s ✓） | 164–165.5 / 164.5–165.5 | 55–56 | 0.2–0.3 ms | 0.0–0.1 ms | 113–207 MB |
| 100,000 | 1431–1725 ms | 164.5–165.5 / 163.5–165.5 | 54–55 | 0.2–0.5 ms | 0.0–0.1 ms | 132–188 MB |

读法：

1. 任务门槛"5 万节点首屏 < 1.5s"达标，且热首屏口径里还含夹具再生成——
   真实场景只会更快；
2. 滚动帧率顶到 rAF 上限（165 Hz 显示器），且 5 万与 10 万节点的每帧绘制
   都在亚毫秒级：说明每帧成本与总节点数无关——视口裁剪（±200 行）与
   静态/动态分层确实生效，这是 T2.2 性能设计的核心验收点；
3. 面板自报 fps 55–56 是它自己的采样口径（统计窗口更保守），与裸 rAF
   计数不矛盾，两者都 ≥ 50fps 门槛；
4. dev 构建（未压缩、带 HMR）下所量；生产构建更快，但低端机 / CI 上
   热首屏会更差。

### 4.3 本节数字不能证明什么

- 4.1 的布局数字**不能**外推为"任何仓库都这么慢"——那是随机 DAG 压力上限；
- 4.2 是单机、单系列测量，只保证量级与"不随总节点数增长"这个结论；
- 没有量：真实 git 仓库（非 mock）端到端的首屏——那取决于分页 IPC 的实际
  往返（深分页 O(已加载行数)，见 `crates/services/src/history.rs` 的说明），
  T2.9 布局缓存落地前不做承诺；迷你地图与拖拽平移的单项帧率也未单测。

## 5. T2.9 补测：历史侧指标、日志分页缓存与性能模式

测量日期：2026-09-29，机器同上（Windows 开发机）。夹具用 `scripts/perf/gen-repo.mjs`
的三个形状；本节所有数字都是 release 构建、**热身一遍之后的第二遍**（首次冷跑
受文件缓存影响，见 §3 的 41 秒教训），单次测量，可信的是量级与相对关系。

### 5.1 新增指标与夹具

- 探针新增：`logFirstPageMs`（首页 200 行，与前端默认页大小一致）、
  `logDeepPageMs`（`--deep-cursor` 处的一页）、`logFirstPageCachedMs` /
  `logDeepPageCachedMs`（同一请求走日志分页缓存的命中口径）、
  `layoutMs`（对首页提交跑一次纯布局）、`detailMs`（提交详情一次）。
- 夹具新增：`--branches N`（主链之外 N 条分支、每 4 条合并回 main，
  同一 fast-import 流内生成，oid 可复现）。

### 5.2 优化前（日志分页缓存落地前）

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| commits-50000 | 139 | 8.7 | 234.0 | 252.6（@25k） | 0.1 | 79.5 |
| commits-100000-br200 | 142 | 8.6 | 466.5 | 541.0（@50k） | 0.1 | 85.0 |

### 5.3 优化后（T2.9：日志分页缓存 LRU(50) + 重查询出主线程）

同一夹具、同一口径（直接数字与缓存命中数字来自同一次进程）：

| 指标 | 直连引擎 | 缓存命中 | 结论 |
| --- | ---: | ---: | --- |
| 50k 首页 | 266.9 | **4.3**（61×） | refs 事件 / 重开页面触发的重复首页几乎免费 |
| 50k 深页 @15k（上限内） | 294.4 | **4.2**（70×） | 累积前缀内任意页都是切片成本 |
| 100k+200br 首页 | 536.6 | **16.8**（32×） | 200 分支的指纹枚举只有几毫秒 |
| 100k+200br 深页 @15k（上限内） | 562.4 | **17.9**（31×） | 同上 |
| 50k 深页 @25k（越过上限 20k） | 294.2 | 296.6 | 绕过路径：与旧行为等价（设计如此） |
| 100k+200br 深页 @50k（越过上限） | 617.9 | 705.7 | 同上；差值在会话噪声内 |
| layoutMs（每页布局） | 0.1 | 0.1 | **布局不是成本**：缓存的是 walk 不是布局 |
| detailMs / statusMs / openMs | – | – | 无回归（同指标 ±15% 会话漂移内） |

与 §5.2 的直连数字相比，直连列整体上浮约 10–15%——那是**会话间噪声**
（后台负载不同），不是代码回归：两条路径的引擎调用在优化前后完全一致，
且有 22 条差分测试与 5 条缓存差分测试钉住结果一致性。

### 5.5 本节落地的三件东西

1. **日志分页缓存**（`crates/services/src/history_cache.rs`）：键 =
   (repo_id, 查询形状, tips 指纹)，LRU 50 条、单条目前缀 2 万条提交、
   全局 10 万条总闸；越过上限绕过直连（旧行为）。差分测试
   `crates/services/tests/history_cache.rs` 钉住"缓存路径与直连路径全等"。
2. **重查询出主线程**：`workspace_status` 与 `git_log_page` 加
   `#[tauri::command(async)]`——Tauri 2 的无 async 命令在主线程（WebView2
   事件循环）上同步执行，万级变更的 6 秒状态计算此前会整窗冻结。
3. **性能模式**（前端，`src/lib/performanceMode.ts`）：auto / on / off 三档
   （设置页可改，键 `history.performanceMode`）；auto 按"状态条目数 ≥ 2000"
   判定，生效时关闭字符级 diff 高亮、diff 上下文压到 1 行（用户点"更多
   上下文"视为显式覆盖）、历史图每页 200 → 100。

### 5.6 nightly 基准回归

`.github/workflows/nightly.yml`（T2.9 第 4 条）：生成三类夹具 → release 探针
（每夹具跑两遍取第二遍，剔冷缓存）→ `scripts/perf/check-regression.mjs` 与
入库基线 `scripts/perf/baseline-ci.json` 比较，任一指标退化 > 10% 失败；
无基线时本次结果成为基线（入 artifact，维护者拷入仓库提交后门禁生效）。

**cron 处于注释状态**：ADR-002 决定私有阶段不启用夜间任务（免费配额），
转公开阶段（T7.2）取消注释即可；当前可用 workflow_dispatch 手动跑。
基线数字是 CI Linux runner 的口径，与本文件 Windows 数字不可互相比较。

### 5.7 本节数字不能证明什么

- 缓存命中的倍数（30–70×）是"重复请求"口径的收益；**第一次**取页没有缓存，
  数字与直连一致——缓存不改变首屏的冷成本，改变的是"第二次起"；
- 深页 @25k/@50k 的绕过路径与旧行为等价（慢但正确），大仓库深翻到 2 万行
  之后仍是逐页 walk——要消除它需要前缀上限之外的结构（按需再做）；
- 全部数字仍是单机、单次测量；性能模式的 auto 阈值（2000 条）是
  "体验开始可感知变慢"的经验位置，未做用户研究。
