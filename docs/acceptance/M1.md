## 2. 覆盖率（`llvm-tools` 离线路径）

本环境装不了 `cargo-llvm-cov`（无外网），改用 rustup 自带的 `llvm-tools`：

```powershell
$env:RUSTFLAGS="-C instrument-coverage"
$env:LLVM_PROFILE_FILE="<repo>\target\cov-profiles\%p-%m.profraw"
$env:CARGO_TARGET_DIR="<repo>\target\cov"      # 与常规构建隔离，避免抢锁
cargo test --workspace --all-features
# 合并（686 个 profraw；分批合并以避开 Windows 命令行长度上限）
& "$env:USERPROFILE\.rustup\toolchains\*\lib\rustlib\x86_64-pc-windows-msvc\bin\llvm-profdata.exe" merge -sparse <profraw...> -o target\cov\merged.profdata
# 报告（--object 传全部测试二进制；stderr 必须丢弃，否则 PowerShell 的报错会混进报告）
& ...\llvm-cov.exe report --instr-profile=target\cov\merged.profdata <exe...> `
    --ignore-filename-regex="(registry|rustup|/target/)" |
  Out-File -Encoding utf8 target\cov-report.txt
node scripts/coverage/summarize.mjs target/cov-report.txt
```

结果（`llvm-cov report` 的行覆盖率，按 crate 聚合）：

| crate | 行数 | 未覆盖 | 行覆盖率 | 阈值 |
| --- | ---: | ---: | ---: | ---: |
| crates/domain | 2808 | 109 | **96.12%** | 85% |
| crates/git-engine | 6736 | 981 | **85.44%** | 85% |
| crates/services | 3427 | 142 | 95.86% | – |
| crates/commands | 2563 | 954 | 62.78% | – |
| crates/storage | 1755 | 105 | 94.02% | – |
| crates/platform | 1309 | 157 | 88.01% | – |
| crates/diagnostics | 430 | 9 | 97.91% | – |
| crates/snapshot | 572 | 140 | 75.52% | – |
| crates/jobs | 334 | 32 | 90.42% | – |
| **整体（不含 src-tauri）** | 19938 | 2632 | **86.80%** | 60% |

说明：

- `src-tauri/src/main.rs` 覆盖率 0%：它是**装配代码**（迁移、注入、命令注册），
  由 `pnpm tauri dev` 与 E2E 验证，不进单元测试。它不计入"整体"，
  否则一个 116 行的装配文件会把阈值判定拉偏——这一点是**口径选择**，
  写在 `scripts/coverage/summarize.mjs` 里，不是随手省略；
- 覆盖率只说明"代码被执行过"，不说明"行为被断言过"。本里程碑的正确性主要靠
  对拍（staging 400 组、引擎差分对拍）与真实仓库集成测试，覆盖率是补充而非替代。

## 3. 受限项与后续动作

### 3.1 10k 变更文件：后端 6.2 s（P1）

数字与三次对照实验见 `docs/PERF-BASELINE.md` §3.1。要点：

- **已修**：状态富化对每个条目做二进制嗅探（打开 + 读 8KB），在 1 万文件上量到
  39–47 秒。git 自己也不在 `status` 里判二进制，已去掉（`enrich.rs`），
  该场景降到 376 ms（未跟踪）/ 6.2 s（已跟踪修改，瓶颈转移到 libgit2 本身）；
- **待决策**：读路径是否从 libgit2 切到 CLI（0.61 s），或按规模分流。
  这是 T1.2 "读用 libgit2" 的架构决策，需要产品确认，**不在收尾任务里单方面改**；
- 界面侧验收（1 万行渲染）通过，且状态面板在等待期间显示骨架屏。

### 3.2 五个真实仓库手测（P1，环境受限）

原定义要求"5 个真实仓库（100 到 100000 提交）"。本环境无外网，无法克隆；
替代方案是 1 个真实仓库 + 6 个可复现夹具，且**走真实服务栈**（不是 mock）。
两者测的能力不同：夹具给的是规模与可复现性，真实仓库给的是"树形状的杂乱程度"。
建议在首次发布前补做：用自己的几个真实项目（含一个有 LFS、一个有子模块）跑一遍
`scripts/perf/run-baseline.ps1`，把数字追加到 `docs/PERF-BASELINE.md`。

### 3.3 `tauri-driver` 闭环 E2E（P1，环境受限）

`crates/` 与 `src/` 的行为验收目前分两层：

- **界面契约层**：Playwright + mock IPC（`e2e/*.spec.ts`，34 例，含 4 条 M1 闭环）；
- **真实 git 语义层**：`crates/*/tests/*.rs` 在真实临时仓库上跑（暂存对拍、提交、
  钩子拒绝、快照回滚）。

缺的一层是"真实后端 + 真实界面"一起跑（`tauri-driver` + WebKitWebDriver，Linux CI）。
本环境没有该驱动，也没有可用的 Linux 显示环境。补做步骤（Linux 机器 or CI）：

```bash
cargo install tauri-driver --locked
pnpm build && cargo build -p forgedesk --release      # 产出可执行文件
tauri-driver --native-driver /usr/bin/WebKitWebDriver &   # 驱动在 :4444
pnpm playwright test e2e/driver/ --project=tauri-driver    # 用 driver 而非 webServer
```

在没有这一层之前，**不要**把"界面点了、后端也真的动了"当成已验证：mock IPC 只能
证明契约（参数与形状），真机上"点了没反应"这类问题只有驱动层能抓。
