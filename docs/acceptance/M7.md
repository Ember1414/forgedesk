## 4. 待人类执行的清单（M7 出口）

> 以下五件事都需要**外部账号、密钥或真机**，编码代理不擅自代劳。

1. **F. 发布凭据与更新通道**（阻塞第 1–4 条验收）
   - 生成更新签名密钥（minisign / Ed25519）与 GPG 发布密钥，**离线备份**；步骤见 `docs/RELEASE.md` §3；
   - 在 GitHub 配置 Secrets / Variables（`TAURI_SIGNING_PRIVATE_KEY`、`TAURI_UPDATER_PUBKEY`、`GPG_PRIVATE_KEY`、`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`）——完整清单与"缺失时的行为"见 `docs/RELEASE.md` §4.1；
   - 建 Cloudflare Pages 项目 `forgedesk`（更新清单与官网同宿主，见 ADR-003）。
   > 更新源与公钥**不进仓库**：由 `scripts/ci/make-build-config.mjs` 在构建时经 `tauri build --config` 注入。
   > 理由（见该脚本文件头）：`createUpdaterArtifacts` 要求公钥存在，而仓库里的配置必须保持"没有更新源"，
   > 否则开发构建会从"静默无更新源"变成"每次检查都网络失败"。
2. **G. 首次实跑发布流水线**：`release.yml` 已写好（tag 触发 → 版本/tag 一致性 → Windows 构建 → 打包 + 校验和 → 签名 → Release → 部署清单），并备好了 4 个脚本与 action 固定策略。
   剩下的是**人类配置凭据后跑一次**（可先用 `workflow_dispatch` + `dry_run` 演练，不产生 Release）：
   核对 `.sig` 的落点与 `latest.json` 里的 `url` 是否指向被签名的那个包（`docs/RELEASE.md` §4.1 的"首次发布时必须核对的两件事"）。
3. **发布演练（T7.10）**：用 `0.7.0` → `0.7.1` 跑一次完整升级（含"篡改包被拒"），再做一次回滚演练（`docs/RELEASE.md` §6–§7）。
4. **Windows 安装包实机验证**：产出 msi/nsis 与便携版 zip 后，在干净环境走"安装 → 打开仓库 → 提交 → push"。
5. **`target/debug` 空间回收**（与本里程碑无关的环境整理）：`Remove-Item -Recurse -Force e:\Projects\ForgeDesk\target\debug\incremental`；本机 `target/` 曾达 71.8 GB。

## 5. 遗留与后续

- **T7.4 未做的部分**：只剩**文件关联**。协议注册（`forgedesk://`）其实早在 T0.11 就随 NSIS 钩子落地（含卸载清理），本报告此前写成"协议注册未配置"是过期表述，已更正。
  文件关联之所以留白：桌面 Git 客户端没有公认的"关联对象"——把 `.gitignore` 关联到某个 Git 客户端会改变用户在编辑器/资源管理器里的既有习惯，
  而"双击打开仓库"在 Windows 上是目录而非文件类型，做不成关联。因此这一项应当**由需求驱动**（真有用户要求时再定关联什么），而不是为了打勾而加。
- **平台暂缓**：macOS / Linux 的安装与更新真机验证推迟到 M8（ADR-005）。CI 矩阵与打包 targets 保留，代码不做平台分支裁剪。
- **e2e 与 nightly 的恢复**：按 `docs/OPEN-SOURCE-READINESS.md` §2，两者在仓库转公开后恢复/启用（配额原因，ADR-002）。
- **供应链**：`pnpm check:workflows` 已从 33 警告降到 **0 警告**（本轮把 32 处 `uses:` 固定到 commit SHA，并给 `compliance.yml` 补上 `concurrency`），OPEN-SOURCE-READINESS 的 C-1 因此闭合。
- **转公开门禁的 A 组已执行**（2026-10-07）：A-2 / A-3 / A-5 / A-6 通过、A-1 以特征式替代通过；发现并脱敏了 `docs/adr/ADR-004` 中回显的个人邮箱（历史侧仅 1 个提交引入，待人类决定清洗或接受）。细节见 `docs/OPEN-SOURCE-READINESS.md` §4。
- **B-10（干净环境可复现）**：需在一台未参与开发的机器上照 `CONTRIBUTING.md` 走一遍，属转公开前的门禁，M7 内不阻塞发布链路搭建。
- **官网的校验和直显（原计划 M8·D8.4，已提前落地）**：Release 附件不返回 CORS 头，页面无法跨域取
  `SHA256SUMS`；解法不是引入代理或第三方，而是让**发布流水线把 `SHA256SUMS` 也放到站点同源路径**
  （`updates/<渠道>/SHA256SUMS`）。因此页面现在会展开一个 `<details>` 直接显示三个 Windows 产物的
  哈希，并与静态的校验步骤并存；`pnpm check:site` 的第三种状态断言"页面显示的值与流水线写出的文件逐字一致"。
  M8·D8.4 剩下的部分是多平台矩阵与校验和的自动渲染样式。

**M7 尚未出口的唯一原因**是发布链路需要人类提供外部凭据（§4·F），以及凭据到位后的一次实跑（§4·G）。
在这些到位前，`0.7.0` 是一个"可自编译、可开发、不可自动更新"的版本——
这正是 `update_check` 返回 `configured: false` 所如实表达的状态。

一条必须记住的边界：**流水线与脚本虽经本地逐项验证，但从未在真实 CI/发布环境跑过**。
首次使用前请按 `docs/RELEASE.md` §4.1 末尾的两条核对项逐条确认（`.sig` 落点、清单 URL 的匿名可访问性与内容一致）。

建议的推进顺序：**F（配置凭据）→ dry_run 演练 → 正式发布 + 发布演练（含"篡改包被拒"与回滚）→ Windows 安装包实机验证 → 转公开门禁（OPEN-SOURCE-READINESS §1）**。
